# 6. Modules and visibility

## Files are not automatically modules

Creating `src/thing.rs` does nothing on its own. Something has to declare it:

```rust
// src/lib.rs
pub mod config;
pub mod palette;
```

The declaration is what pulls the file in. Delete a `pub mod` line and that
file stops being compiled — a common early surprise.

## Two ways to spell a module

```text
src/config.rs           -> module `config`
src/terminal/mod.rs     -> module `terminal`
src/terminal/kitty.rs   -> module `terminal::kitty`
```

A directory module needs `mod.rs`, and it declares its own children:

```rust
// src/terminal/mod.rs
mod detect;
mod kitty;
mod layout;
```

Note those are `mod`, not `pub mod` — the submodules are private. The rest of
the crate cannot write `terminal::kitty::transmit`. That is deliberate.

## Visibility, and why it is a design tool

| Spelling | Visible to |
|----------|-----------|
| (nothing) | the current module and its descendants |
| `pub(crate)` | anywhere in this crate |
| `pub(super)` | the parent module |
| `pub` | anyone, including other crates |

Private is the default, which is the right default.

Look at what [`src/terminal/mod.rs`](../../src/terminal/mod.rs) does:

```rust
mod detect;
mod kitty;
mod layout;

pub use detect::{is_local_ghostty, should_render_image, supports_kitty_graphics, terminal_label};
pub use layout::{greeting_layout, GreetingLayout};
```

Three private submodules, then a `pub use` that re-exports selected items. From
outside, the API is flat:

```rust
terminal::should_render_image(force_kitty)     // callers write this
terminal::detect::should_render_image(..)      // not this
```

**How you organize files and what your API looks like are separate decisions.**
`kitty` is not re-exported at all — the escape-sequence protocol is an internal
detail of how the terminal module draws, and nothing outside needs it. If you
later replace Kitty graphics with Sixel, no caller changes.

`pub(super)` shows up in [`src/pokemon/names.rs`](../../src/pokemon/names.rs):

```rust
pub(super) const NAMES: [&str; 386] = [ ... ];
```

The parent `pokemon` module can see it; nothing else can. The name table is an
implementation detail of species lookup.

## Paths

```rust
use crate::config::Config;    // from the crate root
use super::capitalize;        // from the parent module
use self::detect::...;        // from this module
```

`crate::` is the common one. `super::` appears mostly in test modules, which
need to reach the code they are testing.

## Bringing names in

```rust
use anyhow::{Context, Result};
use crate::palette::{Color, SIZE as PALETTE_SIZE};
```

`as` renames on import. `SIZE` is a fine name inside `palette`, but at a call
site `PALETTE_SIZE` says what it is the size of. Rename when the original name
was clear only in its home module.

Importing a *trait* is required to call its methods, even if you never name it:

```rust
use base64::{engine::general_purpose::STANDARD, Engine as _};
```

`Engine as _` imports the trait anonymously — its methods become available and
the name does not clutter the namespace. You will see this pattern (`use
std::io::Write as _`) whenever a trait exists only to supply methods.

## This crate's module tree

```text
pokefetch (lib.rs)
├── app                 dispatch
├── cli                 argument parsing
├── config              settings
├── icon                .icns generation
├── image_ops           pixel manipulation
├── palette             color extraction
├── pokemon             species lookup
│   └── names           (private) the Pokedex table
├── sprite              sprite sourcing
│   └── bundled         (private) generated by build.rs
├── system              cached machine facts
└── terminal            drawing
    ├── detect          (private) which terminal is this?
    ├── kitty           (private) the graphics protocol
    └── layout          (private) row arithmetic
```

Two things worth noticing:

**Dependencies run one way.** `terminal` uses `palette` and `config`; neither
uses `terminal`. Rust permits cycles between modules, but avoiding them keeps
each module readable on its own.

**`layout` has no I/O at all.** It takes numbers and returns numbers. That is
why it has the most tests in the crate — pure functions are trivially testable,
and pushing logic into them is a design move, not just a tidiness one.

## Splitting a module

`terminal.rs` used to be 442 lines holding three unrelated jobs: talking the
Kitty protocol, computing row offsets, and shelling out to `system_profiler`.
The split was mechanical:

1. `system.rs` — the machine probing, which had nothing to do with terminals
2. `terminal/layout.rs` — the arithmetic
3. `terminal/kitty.rs` — the protocol
4. `terminal/detect.rs` — the environment sniffing
5. `terminal/mod.rs` — what is left: assembling and printing the greeting

Nothing outside the module changed, because `pub use` kept the API identical.
That is the payoff of re-exports: you can reorganize freely behind them.
